# v1 - Tauri 桌面客户端 + Flutter 安卓客户端

## 背景

当前前端仅有 Vue Web 端。v1 目标含桌面端（Tauri，可直接复用 Vue 工程）与安卓端（Flutter，独立工程），三端共用同一套 HTTP + WS 接口。本任务为 v1 收尾里程碑，体量最大，建议在后端 API + WS 协议冻结后批量对接。

## 用户旅程

> ⚠️ **占位符 —— 待头脑风暴**
>
> 本任务的执行模型在启动前，**必须先与用户（tianqingyuluo）进行用户旅程的头脑风暴问答**：围绕"桌面端"与"安卓端"各自的用户旅程、与 Web 端的差异、原生能力逐项探讨，把用户旅程敲定后再落到此处。
>
> 头脑风暴建议覆盖的方向（仅供启发性参阅，最终以问答结论为准）：
> - Tauri 桌面端：直接包 Vue vs 用 Rust 重写部分原生模块？目标平台（Win/macOS/Linux）？
> - Flutter 安卓端：最小支持版本？是否含 iOS（v1 范围外）？
> - 三端功能对齐口径：v1 三端功能集完全一致 vs 桌面/安卓有差异化裁剪？
> - 原生能力：桌面通知、托盘、开机自启；安卓前台服务保活、推送通道（FCM/厂商推送）、麦克风/摄像头权限。
> - 本地缓存：三端是否统一用 idb/SQLite？
> - 离线登录与 token 持久化策略？
> - 更新机制：Tauri 自更新 vs 应用商店；Flutter 应用商店 vs 自分发？
> - 与 [[v1-multi-device-login]]（三端共存）、[[v1-ws-heartbeat-reconnect]]（移动端后台断连重连）、[[v1-user-presence]] 的协同？

> - E2EE（[[v1-e2ee]]）密钥在三端的存储（Keychain/KeyStore）？
>
> 待用户旅程确定后，在此记录编号的端到端步骤，**随后再据此编写下方 e2e 测试**。在此之前 e2e 测试场景保持占位，不得臆造。

## 需求

- Tauri 桌面端：复用 Vue 工程封装，目标平台以结论为准；原生能力（通知/托盘/自启）以结论为准。
- Flutter 安卓端：独立工程，最小版本以结论为准；原生能力（保活/推送/权限）以结论为准。
- 三端共用 HTTP + WS 接口，协议与 Web 端一致，登记到 v1 协议清单。
- 三端功能对齐口径以结论为准。
- 本地缓存、token 持久化、更新机制以结论为准。
- 与既有功能（心跳/重连、多端登录、presence、WebRTC、E2EE）的协同边界以结论为准。
