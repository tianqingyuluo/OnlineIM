# v1 - 离线推送兜底

## 背景

当前在线才收消息，离线期间的消息靠 `GET /api/v1/messages/sync/{conversationId}` 客户端主动拉取。但“上线主动推未读/未收”这一兜底逻辑未见——用户上线后若不点开对应会话，不会知道自己错过了消息。登录成功到 WebSocket 第一次连上之间到达的消息，客户端也要刷新才看得到。本任务补齐连接 / 重连时的未读与漏收推送。

## 用户旅程

> 原 PRD 此节为待头脑风暴的占位符。2026-10-21 按本次实现要求补全（连接或重连时服务端推送自上次见到的 seq 之后的漏收消息，以及各会话未读数和最新预览，含期间的撤回 / 编辑；客户端按消息 id / seq 去重；会话列表和当前聊天不用手动刷新）。对头脑风暴各方向的结论：
> - 上线后**主动推**，不等用户点开。每个连接自己上报游标，服务端只回给这条连接。
> - 不使用 `UserTimeline` 另存漏收。消息仍在私聊 / 群聊集合里，按 seq 读取，因此没有额外清理任务。
> - 量控：每个会话最多 50 条、合计最多 200 条最新漏收；同时给出全部可见会话的未读数和最新预览。超出上限时客户端对**正在查看**的会话再走既有 HTTP 增量。
> - 上线**不算已读**。已读仍由用户看到消息后的 `READ_RECEIPT` 推进。
> - 与在线状态无额外耦合：连接建立成功（含第一次连接和重连）就补齐。
> - 多端各自用自己的 `last_seq` 请求。重复推送由客户端按 `message_id` 丢掉，不重复加未读、不重复插入气泡。

1. 用户 B 不在线（或刚登录、WebSocket 还没连上）。用户 A 在私聊或群里给 B 发消息，也可以随后编辑或撤回。
2. B 的 WebSocket 第一次连上，或断线后重连成功。客户端马上上报每个会话本地已经有的最大 seq，以及当前屏幕上已加载的消息 ID。
3. 服务端回一帧：各会话的未读数和最新预览（已经是编辑 / 撤回之后的样子），加上 B 还没见过的消息（已是当前内容），以及 B 见过但期间被编辑或撤回的消息。
4. B 不用刷新。会话列表的预览、时间和未读角标立刻正确；正在打开的聊天把漏收消息按 seq 补进窗口，已有消息的编辑和撤回也更新。同一条消息不会出现两次，未读不会因为补齐再加一遍。
5. 补齐之后新到的实时消息照常显示，并在不是当前正在看的会话上加未读。
6. 漏收太多、一帧装不下时，正在看的那个会话再向既有增量接口要剩余消息；其他会话至少未读数和最新预览是对的，点开时按历史接口加载。
7. B 的另一台设备用自己的游标各自补齐，不会因为这台设备已经收过就漏掉，也不会把同一条消息算成两条未读。
8. 群消息如果被重复投递（同一条消息再次写入会话记录），未读和“有人@我”只记一次。

## 需求

- WebSocket 连接或重连成功后，客户端发送 `SYNC_REQUEST`，服务端回复 `OFFLINE_SYNC`。
- 推送内容：自客户端 `last_seq` 之后的消息（含期间已撤回 / 已编辑的当前内容）、各会话权威未读数与最新预览，以及客户端已见过但期间被编辑或撤回的消息。
- 单次每会话最多 50 条、合计最多 200 条；`truncated=true` 时客户端对当前会话再调用 `GET /api/v1/messages/sync/{conversationId}`。
- 不把上线当作已读。客户端按 `message_id` 去重，补齐帧不再逐条累加未读。
- 同一条群消息（以及私聊消息）重复写入会话记录时，未读和 @我 不重复增加。
- 登录后、首次连接前到达的消息，在第一次连接成功时补上，不必刷新。
- 会话快照里的 `draft_preview` 一并应用（与会话列表接口相同）。在线状态仍走原有 presence 查询和 `PRESENCE_UPDATE`，不放进 `OFFLINE_SYNC`。用户有多条连接时，只回给发出 `SYNC_REQUEST` 的那一条。

## e2e 测试场景

> 原为占位符。自动化覆盖见“测试范围”的单元测试；下面是在真实 Docker 栈上的手工路径（对应上面的旅程）。

- **E1 离线漏收（旅程 1–4）**：B 断开 WebSocket。A 给 B 发两条私聊、一条群消息。B 重连。不刷新：列表出现这三条的预览和未读，打开中的会话按 seq 补上消息，且没有重复气泡。
- **E2 登录到首次连接的空窗（旅程 2、4）**：B 登录并看到会话列表后，在 WebSocket 连上之前让 A 再发一条。连接成功后该条出现在列表和当前聊天里，未读只加 1。
- **E3 期间的撤回和编辑（旅程 3、4）**：B 离线。A 编辑 B 已经看过的最后一条文本，并撤回另一条 B 还没读的消息。B 上线后，打开的聊天里原文变成新内容并显示“已编辑”，撤回的那条变成撤回提示；列表预览和未读与服务端一致（被撤回且未读的那条不再计入未读）。
- **E4 不重复（旅程 4、5、7）**：补齐帧里的消息随后又被实时帧推一次，气泡仍只有一条，未读不加第二次。补齐之后的新消息仍正常加未读。另一台设备用自己的游标补齐，互不影响。
- **E5 正在查看与量控（旅程 4、6）**：正在看的会话补齐后未读不加；漏收超过单次上限时，当前会话继续用 HTTP 增量补全，列表未读仍是服务端的总数。
- **E6 群未读不双计（旅程 8）**：同一条群消息被会话记录处理两次，成员未读只 +1，“有人@我”只出现一次。
