# v1 - 消息 ACK 与已读回执

## 背景

当前消息发送是单向"即发即忘"：发送方无法确认服务端是否入库、接收方是否收到、是否已读。`Conversation`/消息文档已有 seq 字段，但缺协议层 ACK 与已读上报。IM 基础体验要求：发送方看到"已发送/已送达/已读"三态，群聊维护已读 seq。

## 用户旅程

> ⚠️ **占位符 —— 待头脑风暴**
>
> 本任务的执行模型在启动前，**必须先与用户（tianqingyuluo）进行用户旅程的头脑风暴问答**：围绕"消息 ACK 与已读回执"在私聊/群聊/离线三类场景下的真实预期逐项探讨，把用户旅程敲定后再落到此处。
>
> 头脑风暴建议覆盖的方向（仅供启发性参阅，最终以问答结论为准）：
> - 三态模型（已发送/已送达/已读）是否采用？是否需要区分"已送达"与"已读"两态而非三态？
> - 群聊已读是否显示明细（谁已读）还是仅聚合未读数？隐私偏好？
> - 离线期间回执的行为：上线后是否补发 delivered？还是直接从 read 开始？
> - 已读的判定口径：打开会话即已读 vs 滚动到该消息才算已读？
> - ACK 丢失/重发的超时与重试策略？
> - 未读数语义与既有 `/unread-count/{seqId}` 的兼容方式？
>
> 待用户旅程确定后，在此记录编号的端到端步骤，**随后再据此编写下方 e2e 测试**。在此之前 e2e 测试场景保持占位，不得臆造。

## 需求

- 新增 WS 消息类型：`MESSAGE_ACK`、`RECEIPT`、`READ_RECEIPT`（具体语义以用户旅程头脑风暴结论为准）。
- 消息文档/Conversation 维护已读进度（按 user 维度）。
- `ConversationController` 未读数接口与既有 `/unread-count` 的兼容方式以头脑风暴结论为准。
- 客户端维护本地消息状态机，UI 渲染勾标。
