# v1 - 消息 ACK 与已读回执

## 目标与用户价值

让发送者能够可靠判断消息当前处于什么阶段，并让接收者的阅读行为能够反映到发送者一侧：

- 发送者知道消息是否已经被服务端接受并持久化；
- 发送者知道消息是否已经送达到接收端客户端；
- 发送者知道消息是否已经被接收者阅读；
- 接收者的会话未读数与实际已读进度一致；
- 私聊、群聊、离线重连和多实例部署下都遵循同一套协议语义。

本任务只在用户旅程和协议语义确认后进入技术设计与实现，不直接沿用当前 PRD 中的占位假设。

## 已确认事实（代码与文档核查结果）

1. **任务依赖已满足**：WebSocket 心跳重连和 Redis Stream 消费者组任务已经完成并归档；本任务是当前 v1 基础链路中尚未完成的 P0 子任务。
2. **WebSocket 信封已固定**：所有帧使用 `{ "type": "<TYPE>", "message": {<payload>} }`，协议登记文件为 `docs/ws-protocol-registry.md`。
3. **当前发送链路**：
   - Web 客户端发送 `PRIVATE_MESSAGE_REQUEST` 或 `GROUP_MESSAGE_REQUEST`；
   - 服务端写入 MongoDB 消息文档，生成 `message_id`、`seq_id` 和 `client_message_id`，当前持久化状态为 `0`；
   - 服务端发布 Redis Stream 事件 `PRIVATE_MESSAGE` 或 `GROUP_MESSAGE`；
   - 接收端处理器向发送者和在线接收者发送 `PRIVATE_MESSAGE_RESPONSE` 或 `GROUP_MESSAGE_RESPONSE`。
4. **当前链路缺口**：现有响应同时承担“服务器处理结果”和“接收端收到消息”的作用，没有独立的送达确认与已读上报，也没有回执去重、重放和离线补发语义。
5. **未读数据现状**：MongoDB `Conversation` 已有 `unreadCount` 字段和查询未读数的 Repository 方法，但没有按用户维护的 `readSeq`/已读游标；`ConversationController` 的 `/{conversationId}/unread-count/{seqId}` 当前仍返回 `null`，未形成可用契约。
6. **消息状态现状**：后端消息文档使用数值 `status`，前端 `MessageResponse` 也使用数值状态；前端目前只用本地 pending/超时逻辑渲染发送中的消息和失败重试，没有已送达、已读的 UI 状态。
7. **前端重连基础已存在**：Web 客户端已有出站队列、`client_message_id`、重连后补同步和消息去重相关逻辑；新回执协议必须复用这些标识，不能另造一套客户端消息 ID 或同步游标。
8. **跨端约束已存在**：新增 WS 类型或字段必须登记到 `docs/ws-protocol-registry.md`，并保持 Web、Tauri、Flutter、后端及 proxy 的协议一致。

## 已确认的用户旅程与产品规则

> 本节通过头脑风暴逐项确认。每次用户回答后立即更新本文件，再进入下一个问题。

### 已确认的用户意图

- **发送失败必须是用户可见状态**，不能一直停留在“发送中”；失败消息应提供明确的重试入口或重试反馈。

### 已确认的状态与失败判定

- 用户可见状态至少包含：`发送中`、`发送失败`、`已发送`、`已送达`、`已读`。
- 服务端明确拒绝时立即进入“发送失败”。
- 网络超时不能直接判定为失败；客户端先进入内部“待确认/重试中”状态，界面仍显示“发送中”。
- 客户端复用 `client_message_id` 进行幂等重试；达到重试上限且仍无法确认结果后，才显示“发送失败”。

### 已确认的群聊已读方向

- 群聊 v1 需要能够显示**具体哪些群成员阅读过某条消息**，不能只展示已读人数。
- 服务端仍以每个成员在群会话中的 `readSeq` 作为已读进度的权威数据；某条消息的阅读成员列表可由“成员 `readSeq` 大于等于该消息 `seqId`”推导，避免为每条消息重复存储完整成员数组。
- 阅读进度只允许单调向前推进；重复上报或较旧的 `readSeq` 不得覆盖较新的进度。
- 前端默认显示已读成员头像摘要和已读人数；用户点击后展开完整的成员头像/昵称列表，避免消息流默认被长名单占满。

### 已确认的已读触发规则

- 消息进入前台聊天区域的可视范围并持续可见约 300ms 后，客户端才将其视为已读候选。
- 客户端上报所在会话最新的连续 `readSeq`，而不是为每条消息单独发送一条回执。
- 快速滚动、切后台和重复上报不得导致已读游标回退或产生重复计数。
- 打开会话不会自动把全部历史消息标记为已读；另提供“全部标为已读”作为显式补充操作。

### 已确认的离线处理规则

- 接收者离线时，消息保持“已发送”，不提前标记为“已送达”或“已读”。
- 接收者上线后通过现有 seq 增量同步获取消息；客户端成功接收并写入本地消息库后，才发送送达确认。
- 接收者真正看到消息并满足可视条件后，才发送已读 `readSeq`。
- 发送者离线时，送达状态和已读进度由服务端持久化；发送者重连后通过状态同步获取最新结果。
- 重连和重复同步必须幂等，不得重复增加未读数或回退 `readSeq`。

### 已确认的回执可靠性规则

- 发送请求携带 `client_message_id`，客户端按现有指数退避方式重试；推荐应用层最多尝试 3 次。
- 服务端按 `client_message_id` 去重，重复发送返回原消息确认，不重复创建消息。
- 送达回执按 `message_id` 幂等处理，重复回执直接忽略。
- 已读回执按 `conversation_id + readSeq` 处理，只允许已读游标单调向前推进。
- 重连时通过消息状态和最新已读游标同步恢复，不重放所有历史回执。
- 超过重试上限仍无法确认发送结果时，前端进入“发送失败”状态。

### 已确认的未读数兼容规则

- 保留现有 `GET /api/v1/conversations/{conversationId}/unread-count/{seqId}` 路径。
- `seqId` 继续表示调用方要求统计的起始游标，接口返回该游标之后的未读消息数量。
- 返回体同时包含 `conversation_id`、`from_seq_id`、服务端权威 `read_seq`、当前会话最新 `latest_seq` 和 `unread_count`。
- 会话列表中的 `unread_count` 使用服务端基于当前登录用户 `readSeq` 计算的权威值。
- `READ_RECEIPT` 负责写入已读进度；HTTP 未读数接口负责首次加载和重连后的状态同步。

### 待确认决策

无。用户旅程、状态语义、群聊阅读明细、已读触发、离线处理、回执可靠性和未读数兼容规则均已确认。

## 需求

以下需求基于已确认的用户旅程细化为可测试契约：

- 新增并登记 ACK、送达回执、已读回执所需的 WS 消息类型和字段；
- 服务端能够验证回执发送者身份、会话归属、消息归属和 seq 单调性；
- 私聊按接收者维度持久化已读进度；
- 群聊按用户维度持久化已读进度，并按最终确定的产品语义计算未读数或已读聚合信息；
- 回执处理必须幂等，重复帧不得重复增加未读数或回退已读游标；
- 离线接收者重新上线、重连同步和多实例路由后，消息状态与已读进度最终一致；
- 前端维护与服务端协议一致的消息状态机，并在私聊/群聊 UI 中展示最终确定的状态；
- 保持现有消息历史、`client_message_id` 去重、seq 增量同步和已有 WS 心跳协议兼容。

## e2e 测试场景

测试场景必须逐条映射到最终确认的用户旅程，至少覆盖：

- 私聊消息从本地发送到服务端接受、送达、已读的完整链路；
- 群聊新消息、群成员已读进度与未读数/聚合信息；
- 接收者离线、上线后补发消息和回执的最终一致性；
- ACK/回执重复、乱序、丢失和重连后的幂等恢复；
- 多实例 Redis Stream 路由下发送者、接收者和回执的正确投递；
- Web 客户端状态渲染与核心用户旅程；Tauri/Flutter 协议兼容性验证范围。

## 测试范围

- **单元测试**：状态机迁移、回执校验、readSeq 单调推进、未读数计算、幂等和重复/乱序处理；
- **集成测试**：Controller → Service → Repository、MongoDB 会话/消息数据、WebSocket 单实例全链路、Redis Stream 多实例路由；
- **前端测试**：WebSocket 回执解析、Pinia 状态更新、IndexedDB/重连恢复、私聊和群聊状态 UI；
- **端到端测试**：以最终确认的私聊、群聊和离线旅程为准。

## 已知非目标

- 本任务不重新设计普通消息发送协议之外的业务功能（回复、转发、编辑、撤回、@等由其他子任务负责）；
- 本任务不实现 E2EE、离线推送渠道或多端登录策略，但要为这些任务保留兼容的回执和已读契约；
- 协议命名、方向和载荷以经用户确认的 `design.md` 为准；实现阶段如需调整，必须先回到规划阶段更新契约。

## 依赖与约束

- 依赖 `v1-ws-heartbeat-reconnect`：稳定长连接是回执可靠投递的基础；
- 依赖 `v1-redis-stream-consumer-group`：多实例回执路由和集成测试需要消费者组基础；
- 新增协议必须更新 `docs/ws-protocol-registry.md`，并同步所有客户端边界；
- 所有实现必须遵循现有 MongoDB 消息/会话存储、Redis Stream 跨实例投递和 WebSocket 信封格式。
